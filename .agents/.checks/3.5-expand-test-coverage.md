- Nothing else in this change is hard to reverse

**Renegociação em runtime (registrada antes do código, conforme decisão do usuário):**
`User.ts` hoje é só uma `interface` TypeScript - não compila para nenhum código em runtime, então
não existe "construção/validação" observável para testar sem inventar comportamento (proibido pela
regra 2 do skill). O critério 1 original ("exercita o comportamento observável já definido") e o
critério 3 aplicado a `User.ts` ("deixa de aparecer com 0% de cobertura") contradizem essa realidade
do código. Perguntado, o usuário optou por um teste type-only (`expectTypeOf`/`assertType` do
Vitest), que verifica a forma do tipo em compile-time. Alternativa rejeitada: marcar o critério 1
como Unresolved e não criar `User.test.ts` - rejeitada porque o usuário preferiu ter alguma prova
executável ligada ao arquivo em vez de nenhuma. Consequência aceita: um teste type-only não executa
`User.ts` em runtime, então o v8 coverage não tem como deixar de reportar 0% para esse arquivo - o
critério 3, na parte referente a `User.ts`, fica Unresolved (ver abaixo). A parte do critério 3
referente a `errors/index.ts` segue normal, pois esse arquivo tem código em runtime.

**Correção pós-Verifier:** a primeira versão do teste type-only (`User.test.ts`, com `expectTypeOf`)
não era de fato reforçada por nenhum comando que o projeto roda: `tsconfig.json` exclui
`**/*.test.ts` do `tsc`, e o modo `--typecheck` do Vitest só varre `**/*.test-d.ts` por padrão, então
o arquivo nunca era type-checked e passaria mesmo com o shape de `User` quebrado. Corrigido
renomeando para `User.test-d.ts`, adicionando `typecheck.include: ["src/**/*.test-d.ts"]` em
`vitest.config.ts` e o script `test:types` (`vitest run --typecheck`) em `package.json`. Confirmado
que a prova agora falha de verdade ao injetar um campo incorreto no tipo esperado. Alternativa
rejeitada: remover `**/*.test.ts` do `exclude` do `tsconfig.json` para que `tsc --noEmit` cobrisse o
arquivo - rejeitada por ter efeito mais amplo (afeta a compilação de todos os arquivos de teste do
projeto, não só este) para resolver um problema local a um único arquivo.

## Checks

### S1 - Testes para User e errors · 2 files · 0.4 KB · ~0.1k

**C1** - `User.test-d.ts` verifica, em compile-time, que a interface `User` exige exatamente os campos
`id: string`, `name: string`, `age: number`, `phoneNumber: string`, `email: string`,
`password: string`, `preferredMarketingChannel: string`, sem inventar validação de runtime que o
código não define, e essa verificação é de fato reforçada por um comando que o projeto roda (não
fica inerte)
Proof: `pnpm run test:types` (falha se o shape de `User` divergir do esperado — confirmado
injetando um campo extra no tipo esperado e observando a falha, depois revertido)

**C2** - Para cada uma das 4 classes de erro exportadas por `src/application/errors/index.ts`
(`PasswordDoNotMatchError`, `EmailAlreadyExistsError`, `InvalidMarketingPreferredChannelError`,
`UserCreationError`), instanciar a classe produz uma instância de `Error` cujo `.constructor.name`
é o nome da classe, `.name` é `"Error"` (nenhuma das classes sobrescreve `name`, então o valor
herdado é o comportamento já definido) e `.message` é a string definida no construtor
Proof: `pnpm exec vitest run src/application/errors/index.test.ts`

**C3** - Depois de C1 e C2 implementados, `pnpm run test:coverage` deixa de reportar 0% para
`src/application/errors/index.ts`
Proof: `pnpm run test:coverage` (inspecionar a linha de `src/application/errors/index.ts` no
relatório `text`)

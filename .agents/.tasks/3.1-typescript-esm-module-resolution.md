# 3.1 — Corrigir resolução de módulos TypeScript/ESM para o pipeline real

## Intent

Hoje, `tsconfig.json:9-10` usa `"module": "ESNext"` com `"moduleResolution": "Bundler"` — um modo que pressupõe que um bundler resolve, em tempo de execução, specifiers de import relativos sem extensão. O projeto não usa bundler: o pipeline real é `tsc` (`package.json:6`, `"build": "tsc"`) seguido de `node ./dist/index.js` (`package.json:9`, `"start"`), sob `"type": "module"` (`package.json:4`), que usa o resolvedor ESM nativo do Node — e esse resolvedor exige extensão explícita em specifiers relativos. Isso já é verificável no artefato `dist/index.js` gerado por um `pnpm run build` atual, que contém, por exemplo, `import { buildApp } from "./drivers/app";`, sem extensão. Quem rodar `pnpm run build && pnpm start` hoje corre o risco de uma falha de inicialização (`ERR_MODULE_NOT_FOUND`/`ERR_UNSUPPORTED_DIR_IMPORT`) sem relação com nenhum bug de lógica de negócio.

Depois desta mudança, `tsconfig.json` usa `"module": "NodeNext"` e `"moduleResolution": "NodeNext"`, que exigem — e portanto forçam, em tempo de compilação — que todo import relativo em `src/**/*.ts` carregue extensão `.js` explícita (a extensão do arquivo compilado, não da fonte). `pnpm run build` passa a falhar com erro de tipo caso algum import fique sem extensão, e o artefato gerado roda sob o resolvedor ESM nativo do Node sem depender de um bundler.

## Criteria

### Resolução de módulos alinhada ao pipeline real

1. Quando `tsconfig.json` é atualizado para `"module": "NodeNext"` e `"moduleResolution": "NodeNext"` e `pnpm run build` roda contra o `src/**/*.ts` atual (com imports relativos sem extensão), então `tsc` falha com erro de tipo (TS2835 — "relative import paths need explicit file extensions") — a build não pode passar silenciosamente com um import sem extensão.
2. Depois que todo import relativo em `src/**/*.ts` recebe extensão `.js` explícita, quando `pnpm run build` roda, então ele completa com exit code `0` e zero erros do `tsc`.
3. Quando `node ./dist/index.js` roda logo após um build que satisfaz o critério 2, então o processo não lança `ERR_MODULE_NOT_FOUND` nem `ERR_UNSUPPORTED_DIR_IMPORT` antes do primeiro ponto em que tenta se conectar a uma dependência externa (ex.: banco de dados).

## Decided

| Decision | Shape | Alternative rejected |
|---|---|---|
| Resolução de módulos do projeto segue o modo `NodeNext` do TypeScript, que exige extensão `.js` explícita em todo import relativo — precedente para qualquer arquivo novo em `src/` | `tsconfig.json`: `"module": "NodeNext"`, `"moduleResolution": "NodeNext"` | Introduzir um bundler (ex. tsup/esbuild) para manter `moduleResolution: "Bundler"` válido — rejeitado por adicionar dependência e etapa de build sem necessidade justificada, quando o pipeline `tsc` → `node` já funciona nativamente com `NodeNext` |

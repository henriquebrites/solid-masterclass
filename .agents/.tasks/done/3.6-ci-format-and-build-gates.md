# 3.6 — Adicionar verificações automáticas de formatação e build ao CI

## Intent

Hoje, `.github/workflows/ci.yml` roda type-check (linha 48), lint (linha 51), migrations (linha 53) e testes (linha 57), mas não verifica formatação — Prettier só roda localmente via `lint-staged` (`.lintstagedrc.json:2`), no hook `pre-commit` — nem executa um build real com emissão de arquivos (`tsc` roda só com `--noEmit`). Um push que ignore os hooks locais (ou um ambiente sem Husky instalado) pode chegar ao CI com formatação divergente sem ser barrado, e uma falha de emissão do build não é pega por nenhuma automação hoje.

Depois desta mudança, o CI ganha dois steps novos — verificação de formatação e build real — que falham o pipeline se o código estiver mal formatado ou se a compilação com emissão falhar.

3 criteria in 1 slice · 0 one-way doors · 1 open, of which 0 block

## Criteria

1. Quando `package.json` é inspecionado, então ele contém `"format:check": "prettier --check ."`.
2. Quando `.github/workflows/ci.yml` roda contra um commit corretamente formatado e compilável, então ele inclui um step "Format check" rodando `pnpm run format:check` e um step "Build" rodando `pnpm run build`, ambos terminando com exit code `0`.
3. Quando `pnpm run format:check` ou `pnpm run build` retornariam exit code diferente de zero (ex.: contra um arquivo deliberadamente mal formatado, ou um import sem a extensão exigida por 3.1), então o step correspondente do CI falha e o pipeline reporta falha — verificado exercitando cada step contra essa mudança em revisão, não fazendo merge de uma.
